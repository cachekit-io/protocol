### SaaS API — clients reject the empty cache key (LAB-6548)

- [`spec/saas-api.md` → Cache-Key Path Encoding](spec/saas-api.md#cache-key-path-encoding),
  rule 2: clients MUST reject an empty key before building the URL, as they already
  reject `.`, `..`, `health`, `ttl` and `lock`. An empty key encodes to an empty segment,
  so `/v1/cache/{key}` becomes `/v1/cache/`, the collection path rather than a keyed
  resource.
- [`test-vectors/path-encoding.json`](test-vectors/path-encoding.json) 1.1.0: one
  `reject: true` row for the key `""`, and the `contract` text names the empty key among
  the reject rows. Counts: 16 rows, 6 of them reject rows.
- [`tools/path-encoding-verify.py`](tools/path-encoding-verify.py) adds `""` to the
  reserved set, and its self-test gains a mutation that gives the empty-key row the
  empty string as its `encoded` value.
- [`sdk-feature-matrix.md`](sdk-feature-matrix.md): the Python and Rust path-encoding
  cells are ⚠️ Partial until those SDKs reject the empty key.
- **Breaking for SDKs that accept an empty key, and for their callers:** an SDK must now
  raise before building the URL when the key is `""`, and a caller passing `""` to the
  CachekitIO backend gets that client-side error. Migrate by passing a non-empty key. An
  empty key never addressed a stored entry, so no cached data is lost.
