### SaaS API — the writer's own local copy is bounded, and `/ttl` states its rounding

- **New SDK MUST: the writer's own copy** ([Remaining Freshness](spec/saas-api.md#remaining-freshness)).
  Once the store accepts a `PUT`, the SDK's local copy of that value MUST NOT be served in
  any form after `min(local_ttl, effective_ttl)`, measured from receipt of the `2xx`. The
  spec states the accepted error as the write-path tolerance, and the re-serving-tier decay
  rule carries the same sub-second tolerance. A copy kept without a `2xx` MUST be timed from
  no later than its local write, and SHOULD be timed from the first dispatch of the `PUT`.
  The revocation bound now covers the writer's copy.
  **Affects SDKs** whose local copy of a write outlives the TTL they send on the wire.
- **`GET /v1/cache/{key}/ttl` rounding** ([endpoint](spec/saas-api.md#get-v1cachekeyttl)):
  `ttl` is `evict_at − floor(now)`, the remaining lifetime rounded up. It reads `1` in the
  final sub-second, and the endpoint returns `404` from `evict_at` on. `X-CacheKit-Fresh-For`
  rounds the other way. This documents the deployed server; no behaviour changes.
- **Revalidation `PUT`** ([write semantics](spec/saas-api.md#write-semantics)): a recompute
  stores a no-expiry entry only when it carries neither `X-CacheKit-TTL` nor legacy `X-TTL`,
  as the effective-TTL definition already implied. SDKs MUST still re-send `X-CacheKit-TTL`.
- **Feature matrix:** the Rust and TypeScript client-L1 stale-while-revalidate cells now
  read refresh-ahead within the L1 TTL, never served after it, with code citations in
  note ¹⁰. The Python server-bounded L1 backfill cell is ⚠️ from `cachekit` 0.19.0: the
  bound ships, but the header value is not parsed to the spec's grammar.
