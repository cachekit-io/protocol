### Interop v2 — item 7 states what a 32-bit target must run, and at which limits (LAB-6390)

- [`spec/interop-v2.md` → SDK Implementation Requirements](spec/interop-v2.md#sdk-implementation-requirements),
  item 7, now defines "supports a 32-bit target": the implementation compiles
  for, or publishes artifacts for, that target. It runs
  `lz4_ratio_product_wraps_32_bits` in its own CI on each such target, at this
  spec's limits. A rejection for any reason, a stricter configured limit
  included, is a failure. Before, the limits rule sat only in the Test Vectors
  table, so a reader of the checklist could take the vector's rejection for an
  expected deployment-limit rejection, which looks the same as a 32-bit wrap.
- [Security Limits](spec/interop-v2.md#security-limits-decompression-bounds)
  says its permission for stricter deployment limits does not apply to a
  conformance run. The Test Vectors row and the Security Limits prose point to
  item 7 instead of restating it.
- [`test-vectors/interop-v2.json`](test-vectors/interop-v2.json) stays at
  **1.1.0**, which is unreleased. Two metadata strings change and no vector
  bytes do. `construction_note` states the segment rules (non-empty even-length
  `hex`, integer `count` ≥ 0, a total equal to the declared length) in words
  instead of as a Python expression. The description of
  `lz4_ratio_product_wraps_32_bits` points to item 7 instead of restating it.
- [`tools/interop-v2-crosscheck.mjs`](tools/interop-v2-crosscheck.mjs) refuses a
  construction whose declared length is above the spec's limit for its field,
  before it allocates. A fixture declaring gigabytes used to allocate them when
  its segment counts agreed with the declared length.
  [`tools/test-interop-v2-crosscheck-guard.mjs`](tools/test-interop-v2-crosscheck-guard.mjs)
  covers the container field and the value field.
- The Regenerate / verify block lists the two mutation suites CI runs.
