### Conformance — encryption and cache-key-format requirement ids

- **Requirement ids**: every MUST and MUST NOT in [encryption.md](spec/encryption.md)
  (`ENC-1` to `ENC-10`) and [cache-key-format.md](spec/cache-key-format.md) (`KEY-1` to
  `KEY-12`) now carries an id, indexed in
  [conformance/requirements.json](conformance/requirements.json) and reported per SDK in
  [conformance/coverage.md](conformance/coverage.md). No normative text changed;
  `tools/conformance.py strip` removes the ids. The pseudocode block in
  [Pseudocode for SDK Implementors](spec/cache-key-format.md#pseudocode-for-sdk-implementors)
  is marked not-a-requirement: its two MUSTs, in code comments, restate `KEY-6` and `KEY-11`.
- **What the new mappings show**: of the 22, 11 are partly pinned by vectors and 11 by
  nothing. None is fully pinned: even the frozen `True`/`False` tokens (`ENC-6`) are
  pinned only as a renderer's output, since no vector shows the AAD an SDK's write path
  emits. The key-format rules bind cachekit-py, the only SDK that writes keys in
  this format and offers more than one serializer; the two `ns:` rules and the
  forward-only keyring rule bind application code. No vector reaches the no-retry rule,
  the post-decryption container rules or the keyring configuration rules, because every
  encryption vector is a valid entry that a reader decrypts: none presents tampered
  metadata, a container the reader must refuse, or a keyring configuration to reject.
  [cache-key-format.md](spec/cache-key-format.md)'s Server-Side Requirements hold no
  hard keyword, so no id in either file binds the server.
