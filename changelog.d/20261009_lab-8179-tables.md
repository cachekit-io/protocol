### Test vectors — encryption.json 1.5.0 and cache-keys.json 1.3.0 add reject, container, keyring-configuration and serializer-object tables (LAB-8179)

- [`test-vectors/encryption.json`](test-vectors/encryption.json) `1.5.0` adds three tables. No existing vector
  changed.
  - **`aad_reject_vectors`**: eight rows that present six published ciphertexts under AAD inputs that differ from the
    ones they were sealed under in one component: the other `compressed` value either way, with four and with five
    components, `msgpack` for `arrow`, `original_type` dropped and added, and the cache key with a prefix in front.
    Each row has a vector's fields plus `sealed_as` and `note`, so a harness can run its decrypt path on it and
    assert that authentication fails. A reader that retries with the input a row was sealed under decrypts it.
  - **`decrypted_container`**: six plaintexts sealed under the AAD of the reader each names in `reader`
    (`plain_msgpack`, `bytestorage_envelope`, `arrow_checksummed` or `orjson_checksummed`), in a container that
    reader is not configured for or must not unwrap. `outcome` says what a conforming read gives: `error`, no value,
    or `not_unwrapped`, anything but the value inside the envelope. A reader that sniffs the plaintext, falls back to
    another container, or ignores bytes after the first document returns a value one of them forbids.
  - **`keyring.configuration`**: four configurations a keyring is loaded from, with the `verdict` a conforming SDK
    gives at load: three decrypt-only keys (accept), four (reject), and the current key repeated in the decrypt-only
    list as given and in uppercase (reject either way, whatever an SDK does with uppercase hex).
- [`tools/encryption-verify.py`](tools/encryption-verify.py) verifies each table: it pins what each row presents or
  holds, models each mistake a note names as a retrying reader, a wrong container reader or a wrong loader that must
  misjudge its row, and refuses a row whose verdict turns on something the spec leaves open.
  [`tools/test_encryption_verify.py`](tools/test_encryption_verify.py) adds mutation cases for the new guards; the
  seal-lane check that a reject row does not authenticate has none, since the one-input rule already implies it.
- [`test-vectors/cache-keys.json`](test-vectors/cache-keys.json) `1.3.0` adds two tables. No existing vector changed.
  - **`error_vectors`**: an empty, a `null`, a `0` and a `1` serializer identity, which key generation must refuse
    with an error.
  - **`serializer_object_vectors`**: the serializer as a class a test instantiates and configures a cache with
    (`serializer_class`, and `defined_by`: the SDK's own class or one the test defines). cachekit-py's four built-in
    serializers key under their `<custom>:` identities, never their table codes, and a class named `auto` keys as
    `xf932`, never AutoSerializer's `a`.
  cachekit-py 0.22.0 passes every row.
- [`spec/encryption.md`](spec/encryption.md) and [`spec/cache-key-format.md`](spec/cache-key-format.md) describe the
  new tables. No normative text changed.
- [`conformance/coverage.md`](conformance/coverage.md): KEY-2, KEY-6 and KEY-9 drop their gaps. ENC-1, ENC-7, ENC-9
  and KEY-10 move from gap only to vectors and a gap, and ENC-2 and ENC-3 list the container rows with narrower
  gaps. Every SDK reads them uncovered or partial until it re-vendors.
