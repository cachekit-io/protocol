### SDK feature matrix and intent presets — Rust cells brought to the published cachekit-rs 0.8.0 (LAB-5291)

- Every flip below was verified against the published `cachekit-rs-0.8.0.crate` (crates.io,
  2026-09-30), not the repository branch. TypeScript cells are unchanged.
- **`secure` spelling.** Rust spells the encrypted preset `CacheKit::secure` and the
  `SecureCache` accessor `secure_cache()` from 0.8.0; 0.7.0 and earlier spell them
  `CacheKit::encrypted` and `secure()`. The [intent-presets](spec/intent-presets.md#sdk-conformance)
  "spelled `secure`" row is ✅ for Rust, and rule 3 no longer records a non-conformance.
  [Matrix](sdk-feature-matrix.md#developer-experience) footnote ¹¹ now gives the 0.8.0 floor,
  its line references resolve in the 0.8.0 crate, and it warns that the upgrade also changes
  the key argument from raw bytes to hex: pass `hex::encode` of the bytes 0.7.0 received to
  keep reading existing entries.
- **Companion env constructors (new normative rule).** New
  [Explicit Configuration](spec/intent-presets.md#explicit-configuration) rule 4: in a
  language without optional arguments, the `secure` and `io` environment fallbacks MAY be a
  constructor that takes no key argument (Rust `secure_from_env`, `io_from_env`); it is the
  same preset, not a further name. It MUST read that preset's environment configuration —
  `CACHEKIT_MASTER_KEY` and `CACHEKIT_PREVIOUS_MASTER_KEYS` for `secure` (or fail at
  construction when the previous-keys variable is set), `CACHEKIT_API_KEY` only for `io` —
  and MUST NOT read a variable that changes encryption activation. Rust `secure_from_env`
  ignores `CACHEKIT_PREVIOUS_MASTER_KEYS`, so a new conformance row records it as ❌.
- **`minimal` L1.** On in Rust from 0.8.0 (1 000 entries, stale-while-revalidate off); off on
  0.7.0 and earlier. The conformance row is ✅.
- **Hex master key.** `CacheKit::secure(url, master_key_hex)` takes a hex string (at least
  32 bytes, exactly 32 recommended) and `CacheKit::secure_from_env(url)` reads
  `CACHEKIT_MASTER_KEY`, failing at construction when it is unset or empty. The hex and env
  halves of the conformance row are ✅; the raw-bytes length clause stays ❌, because the
  raw-bytes entry points still accept more than 32 bytes.
- **`io` credentials.** `CacheKit::io(api_key)` or `CacheKit::io_from_env()`, which reads only
  `CACHEKIT_API_KEY`. The conformance row is ✅ for Rust.
- **Keyring rotation.** Released in Rust from 0.8.0 (at most three previous keys). The
  [matrix](sdk-feature-matrix.md#encryption) row, note ⁵,
  [encryption.md](spec/encryption.md#key-rotation-keyring) and the
  [decision record](decisions/key-rotation.md) now say so; TypeScript stays unreleased at
  npm 0.1.5. In Rust only `from_env()` reads `CACHEKIT_PREVIOUS_MASTER_KEYS`; the `secure`
  preset's `secure_from_env` ignores it, so a `secure` client passes decrypt-only keys through
  the builder.
- **Hardware-acceleration detection and observability.** The Rust hardware-acceleration row
  and the Rust metrics, structured-logging and SaaS-telemetry rows are ✅ from 0.8.0.
- **Compliance Status.** Rust rejects the five reserved path segments since 0.8.0 (the
  empty-key half stays open), and vendors `interop-mode.json` 1.1.0 and `decode-bounds.json`
  1.1.0 since 0.8.0; note ¹⁶ says so. Fixture 1.2.0 stays unreleased in Rust.
- **Note ¹⁹** (`workers` feature) is rewritten against the 0.8.0 crate: every item that
  encrypts is feature-gated, the builder's encryption methods are no-op stubs without the
  `encryption` feature, and the plain `get`/`set` path never encrypts.
