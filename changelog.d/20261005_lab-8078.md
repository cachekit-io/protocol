### Conformance — SaaS API requirement ids

- **Requirement ids**: every MUST and MUST NOT in [saas-api.md](spec/saas-api.md)
  (`API-1` to `API-74`) now carries an id, indexed in
  [conformance/requirements.json](conformance/requirements.json) and reported per SDK in
  [conformance/coverage.md](conformance/coverage.md). No normative text changed;
  `tools/conformance.py strip` removes the ids. The sentence in
  [Cache-Key Path Encoding](spec/saas-api.md#cache-key-path-encoding) that says MUST and
  MUST NOT are used as in RFC 2119 names the keywords as words, so both are marked
  not-a-requirement.
- **What the new mappings show**: 25 of the 74 bind the server, 4 bind application code or
  its deployment and 45 bind SDKs. Five of the SDK rules apply only to an SDK that writes a
  stale window or revalidates a server-stale hit, which only cachekit-py does, so they bind
  cachekit-py alone. Only the cache-key path-encoding rules have vectors: 12 are partly
  pinned by `path-encoding.json` and 62 by nothing. None is fully pinned. The rows pin an
  SDK's encoder, not the path of the request it builds, and no row holds a backslash
  (which a WHATWG URL parser reads as `/`), a byte outside ASCII, `-`, `~`, or most of the
  ASCII delimiters (`" $ & + , ; < > @ [ ] ^ { | }` and the backtick). No public vector
  exercises the server, so every server requirement is a gap, and none covers request or
  response headers, an SDK's local cache, its lock client or its revalidation flow.
