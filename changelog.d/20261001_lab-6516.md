### Interop v2 — the 32-bit ratio vector's original is larger than its payload (LAB-6516)

- [`test-vectors/interop-v2.json`](test-vectors/interop-v2.json) **1.3.0** rebuilds
  `lz4_ratio_product_wraps_32_bits`. The payload is still exactly 4,294,968 B, but
  the LZ4 block now expands: a literal run followed by an offset-1 match of zeros,
  then the 5-literal final run. `original_size` goes from 4,278,189 B to
  8,523,079 B, larger than the payload. Before, a reader that accepted any
  `original_size` no larger than the payload before computing the ratio product in
  32 bits passed the vector, and then wrongly rejected real containers with a
  payload of 4,294,968 B or more whose `original_size` exceeds both the payload and
  the wrapped bound. It now fails the vector. Readers MUST still accept it and decode it
  to the constructed value. No other vector changes.
- [`spec/interop-v2.md` → SDK Implementation Requirements](spec/interop-v2.md#sdk-implementation-requirements),
  item 7: a package that distributes a build of an interop/v2 implementation for a
  32-bit target is itself such an implementation, whichever repository the code
  comes from. The [Test Vectors](spec/interop-v2.md#test-vectors) row now states
  which readers the vector fails, not that it fails every 32-bit reader.
- **CI guard**:
  [`tools/test_interop_v2_reference.py`](tools/test_interop_v2_reference.py) adds
  a fourth 32-bit reader, the fast path above. The coverage guards in the reference
  self-check and in
  [`tools/interop-v2-crosscheck.mjs`](tools/interop-v2-crosscheck.mjs) now also
  require a discriminating vector's original to be larger than its payload, and
  both mutation suites show they refuse a literals-only block of the same size.
  The Python suite also checks the ratio bound directly, one byte either side of
  1000:1, so a reader with no ratio check or a strict `<` now fails it.
- No SDK vendors `interop-v2.json`, so nothing downstream needs re-vendoring.
