### Encryption — the AAD's `cache_key` is the logical backend key

- The [`cache_key` AAD field](spec/encryption.md#additional-authenticated-data-aad) is now
  defined as the **logical backend key**: the UTF-8 string the client passes to its backend.
  It is taken after every client-side prefix, whether an SDK namespace (for example a Rust
  client's `.namespace()`) or a prefix the backend adds (for example ioredis `keyPrefix` or
  a Memcached backend's `keyPrefix`). It is taken before any encoding the backend uses to
  address its store, such as percent-encoding, the File backend's BLAKE2b-128 file name or
  a Cache API URL. It never includes scoping a server applies after it receives the key,
  such as the SaaS's per-tenant storage. Ciphertext moved to another namespace or prefix
  under the same master key and tenant must fail authentication. Un-namespaced,
  un-prefixed and interop-mode keys are unchanged: interop mode already rejects both
  prefixes.
- **Breaking for encrypted entries written under a namespace or key prefix by an SDK that
  bound the key without it:** once that SDK follows this definition, those entries no
  longer authenticate. Delete them, or move to a fresh namespace or prefix, rather than
  waiting out their TTL. The [no-retry rule](spec/encryption.md#additional-authenticated-data-aad)
  now names a different `cache_key` form, so a reader MUST NOT fall back to the key
  without its namespace or prefix.
