### Encryption — the AAD's `cache_key` is the logical backend key

- The [`cache_key` AAD field](spec/encryption.md#additional-authenticated-data-aad) is now
  defined as the **logical backend key**: the full UTF-8 key including every client-side
  prefix, whichever client-side layer adds it — the SDK (for example a Rust client's
  `.namespace()`), its backend (for example a Memcached backend's `keyPrefix`) or the
  backend's client library (for example ioredis `keyPrefix`). It excludes any encoding the
  backend uses to address its store, such as percent-encoding, the File backend's
  BLAKE2b-128 file name or a Cache API URL. It never includes scoping a server applies
  after it receives the key, such as the SaaS's per-tenant storage. Ciphertext moved to
  another namespace or prefix under the same master key and tenant must fail
  authentication. A key with no namespace or key prefix is unchanged. That covers interop
  mode: [interop keys are identical across SDKs](spec/interop-mode.md#encryption-in-interop-mode),
  so an interop entry carries neither, and its AAD is unchanged.
- **Breaking for encrypted entries written under a namespace or key prefix by an SDK that
  bound the key without it:** once that SDK follows this definition, those entries no
  longer authenticate. Delete them, or move to a fresh namespace or prefix, rather than
  waiting out their TTL. The [no-retry rule](spec/encryption.md#additional-authenticated-data-aad)
  now names a different `cache_key` form, so a reader MUST NOT fall back to the key
  without its namespace or prefix.
